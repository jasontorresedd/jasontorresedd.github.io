Mobile Data

Dashboard

This is an introduction to a dashboard developed as a side project and just for fun. Inspired by a training I designed for a client, I began wanting to experiment with designing and developing my own dashboard with Claude. Recalling a dataset I have created over 10 years of tracking my own mobile data use across carriers and devices, I decided to turn this data into an interactive dashboard. This was my first attempt planning, designing, and developing a dashboard with Claude.

Story

Since 2016 I have kept a monthly record of my mobile data usage across 2 carriers, multiple iPhones, multiple iPads, and their hotspots. It started when I was on a 4G (LTE) unlimited service, then transitioned to a 5G unlimited service, as well as through COVID-19 and iOS bugs. This dataset has just become a habit and I haven't thought much about it. But while designing an AI training for Oliver Wyman in September 2026, I got to thinking about how I could convert this dataset into a dashboard. I found myself writing the steps to do this as part of creating a learning activity, so I thought, why not give it a go with my own data? For me at least, the result is a pretty cool story of life and the mobile devices that were literally closest to me.

Why it was built

Reason 1: To practice the skill of storytelling with data. I wanted to think through and imagine what I could visually communicate through a series of charts, graphs, and simple color, using data that I know quite well.

Reason 2: To provide a demonstration of what I could create with Claude Code when taking a real dataset and turning it into a visual story. The results were guided by ideating a story, preparing data, thinking as a machine, and preparing materials to guide Claude.

The data source

This data has been collected by me from the start of 2016 to the present day. I have a routine for resetting the data counters on my devices and at each point that I do this, I jot down in a spreadsheet how much data I've used. It is purely the whole amount and is not broken down by categories of use.

Development

There were four phases to developing the dashboard. See below to learn about each phase. While some of these relied solely on my effort, others were done for or in partnership with Claude.

01

Data preparation

The existing spreadsheet was minimally formatted with colors, separated rows, formulas, and comments that would be problematic for Claude to read. Additionally, the data was kept in an uncommon file format. Over a few hours, I reformatted the data into an XLSX file and removed all of the formatting and ensured a complete set of rows and columns. When organized, rows represented devices and hotspots, and columns represented months and years.

While creating the spreadsheet I realized that I needed to help Claude recognize that active or inactive mobile data consumption needed to be understood in relation to the ownership status of a device. So to do this, I created a secondary spreadsheet with the same row and column format, and set the following in cells: 0 = Unowned device and inactive hotspot; 1 = Owned device and active hotspot; and 2 = Owned device and inactive hotspot.

02

Designing the style board

For styling, I first thought about different colors for data, but soon realized this would not be good. Because data carriers (Sprint and Verizon) were so central to the story, I needed to use their colors and neutrals for everything else.

With colors settled, I browsed Google Fonts to select some fonts I had not tried before. This didn't take too long as I already had a sense of what I was looking for even though I didn't know exactly what.

Finally, I used the Design feature in Claude to create a style board to guide how these and other design elements would work together to tell a data story. When done, I exported the style guide as Markdown to share with the instructions I would write for Claude.

03

Instructions development

At this point I sat down and wrote out a full set of background, context, and instructions for Claude guiding how I wanted it to understand what I was providing and what I wanted to build. My instructions included six sections: 1) overview, 2) audience, 3) data sources, 4) presentation, 5) target output, and 6) technical specifications. Within this I provided details on how to understand the data, how to recognize the devices listed, how to distinguish the two spreadsheets provided and use them together, and what kinds of functions and cards I was looking for a user to see in the dashboard. These instructions were saved as Markdown.

04

Development procedure

This phase was only begun once data preparation, the style board, and the instructions were settled. Of those, I iterated with Claude on the style board a bit more after it was drafted, and I walked away and returned to the instructions a few times as I did other work. But once those were done, I did the following:

  • Step 1: Prior to development, I used Google Gemini 3.1 Pro on 'High' effort to generate SVG images of each iPhone and iPad device that is represented in my data. I looked for other options first, but this was the easiest thing to do with surprisingly good output.
  • Step 2: Created a project folder on my desktop and included the instructions and style guide in Markdown, a folder with fonts, a folder with device images, and the full dataset and ownership guidance spreadsheets in CSV files. I also included blank HTML and JS files following the file names I outlined in the instructions, and a CSS file following the same file naming in the instructions, but including the basic layers I wanted the CSS built within.
  • Step 3: Opened the folder in VS Code and launched the Claude Code plug-in.
  • Step 4: Instructed Claude to read my instructions and the style guide in the project folder, then execute on those. I used Opus 5.5 and set effort to 'High'.
  • Step 5: After about 15 minutes, Claude had drafted the HTML, CSS, and JS files I had asked for. I reviewed these before going forward to gain orientation and see how it drafted the dashboard against my instructions and style guide.
  • Step 6: From here I went through a couple of hours iterating with Claude on all aspects of the dashboard. This included redesigning cards, adding cards, and dropping cards. While doing this, I would manually revise language in the HTML and JS files. Before finalizing I asked it to make a pass to identify any typos or coding errors that needed fixing.
  • Step 7: I conversed with Claude on how this would be released on GitHub Pages. Initially, the dashboard relied on the presence of the CSV files to properly load the site. I worked with Claude to build the necessary data into the JS file. This is fine for me because the dashboard is for demonstration only.
  • Step 8: In the last step of development Claude produced a revised version of the style guide incorporating all design changes we made. I then archived the work and moved relevant project files into my GitHub repository.

Style

Functions

The following are a few functions that you can operate within the dashboard.

Light and dark themes
Toggle between light and dark viewing in your browser.
Devices and carrier
Select between viewing devices as glyphs or images, and switch the carrier in view.
Comprehensive chart controls
Change the view, series, and time span, compare years, and flag anomalies and markers.
Small screen notice
Built for tablets and larger. Phones see a notice in place of the dashboard.
